# DeaDBeeF — working notes for Claude

DeaDBeeF is a modular cross-platform audio player (Linux, macOS, Windows). The core is written in C,
and most features are plugins that use the C API in `include/deadbeef/deadbeef.h`. The macOS UI is Objective-C
(`plugins/cocoaui`). The Linux/Windows UI is GTK2/GTK3 (`plugins/gtkui`). The project has no Swift code; don't add Swift
unless asked.

## Folder structure

| Path | What it is |
| --- | --- |
| `include/deadbeef/` | Public plugin API (`deadbeef.h`, `common.h`, ...). Changing it affects ABI: bump API versions and keep backward compat |
| `src/` | Core: playlist, streamer, metacache, junklib (tags), title formatting (`tf.c`), vfs, conf, dsp, plugins loader, undo |
| `shared/` | Code shared by 1st-party plugins but not exposed via the API (parser, ctmap, scriptable, undo, analyzer/scope, trkproperties_shared, ...) |
| `plugins/<name>/` | One directory per plugin (decoders, outputs, DSP, GUIs, medialib, artwork, lyrics, converter, ...) |
| `plugins/cocoaui/` | macOS app UI, grouped by feature subfolders (`Playlist/`, `Preferences/`, `DesignMode/`, `MediaLibrary/`, `Widgets/`, `XIB/`, ...) |
| `plugins/gtkui/` | GTK UI (`interface.c`/`support.c` are generated by Glade from `deadbeef.glade`; don't hand-edit them unless that's the established practice for the change) |
| `osx/` | Xcode project `osx/deadbeef.xcodeproj`, xcconfigs, `IntegrationTests/`. `osx/deps` is a submodule with prebuilt deps |
| `Tests/` | Unit tests (GoogleTest `*.cpp`, plus some XCTest `*.m`/`*.mm`), test data in `Tests/TestData` |
| `external/` | Third-party / separate repos (mostly git submodules) |
| `po/`, `translation/` | gettext translations (GTK side) |
| `scripts/`, `ci_scripts/`, `tools/`, `.github/workflows/` | Build, packaging, CI |

Build systems: autotools (`configure.ac`, `Makefile.am` per dir) for Linux, premake (`premake5.lua`) for Windows,
Xcode for macOS. Generated files (`Makefile.in`, `configure`, `config.h`, `autom4te.cache`, `testbuild/`) are untracked
build artifacts; don't edit them. When adding or removing source files, update **every** relevant build system: the
`Makefile.am` of that dir, `premake5.lua`, and the Xcode project (use the Xcode tools to add files to targets).

How to tell, in general:
- A file header that says *"This file is part of Deadbeef Player source code"* / *"Copyright (C) ... Oleksiy Yakovenko"*,
  or the Xcode-style header *"Created by Oleksiy Yakovenko"*, means 1st-party. Other copyright holders and upstream
  library layouts (own `COPYING`, `README`, `include/`, `src/`, versioned dir names) mean third-party.
- In a plugin dir, the top-level glue files (`plugin.c`, `<name>.c`, `*wrap.cpp`, etc.) are usually 1st-party, and the
  nested library subdirectory is third-party.
- If unsure, check `git log` for the file and its license header before modifying it.

## Coding style (1st-party code)

`.clang-format` at the root describes the style. Match the surrounding code, and don't reformat lines you aren't changing.

C / C++ / Obj-C common:
- 4-space indentation, no tabs, 120-column limit.
- K&R braces on the same line (functions too), `else` on a **new line** after `}`:
  ```c
  if (x) {
      ...
  }
  else {
      ...
  }
  ```
- Always use braces, even for one-line bodies. No single-line `if`/loops/functions.
- A space before the opening paren in C function calls and declarations: `foo (a, b)`, `sizeof (x)`, `if (`, `for (`.
  (Older/newer code is sometimes inconsistent; follow the file you're in.)
- Return type on its own line for top-level C function definitions and prototypes:
  ```c
  static int
  pnull_play (void) {
  ```
- Pointer star binds to the name: `char *s`.
- Preprocessor indent after hash: `#    define`.
- Names are `snake_case` for C functions, variables, and types; public API types use `ddb_`/`DB_` prefixes
  (`ddb_playItem_t`, `DB_functions_t`). Static helpers inside a plugin take the plugin prefix.
- Prefer `static` for file-local symbols. Plugins access the core via a global `static DB_functions_t *deadbeef;`
  (cocoaui: `extern DB_functions_t *deadbeef;`) and expose a `<name>_load (DB_functions_t *api)` entry point.
- Debug tracing: the `//#define trace(...) { fprintf(stderr, __VA_ARGS__); }` / `#define trace(fmt,...)` pattern,
  or `deadbeef->log_detailed` / `deadbeef->log`.
- Memory/refcounting: playlist items and playlists are refcounted (`pl_item_ref`/`pl_item_unref`,
  `plt_ref`/`plt_unref`). Every get/alloc must be balanced. Use `pl_lock`/`pl_unlock` around playlist traversal.
  Metadata strings come from the metacache (`metacache_add_string`/`metacache_remove_string`) where applicable.
- C code should stay portable (Linux/macOS/Windows via mingw). Guard platform code with `#ifdef __APPLE__`,
  `#ifdef __linux__`, `#ifdef _WIN32`.
- New 1st-party C files get the zlib license header block like in `src/streamer.c` (see `shortlicense.zlib`).
  Plugins may be GPL/LGPL; check the plugin's `COPYING` and match the neighbors.

Objective-C (cocoaui):
- Xcode-template file header (`//  File.m`, `//  DeaDBeeF`, `//  Created by ...`, `//  Copyright © YEAR Oleksiy Yakovenko. All rights reserved.`).
- `#import` for Obj-C headers, ARC, `@property (nonatomic)` with class extensions for private state.
- Method braces are usually on the same line: `- (void)foo {`. Early-return guard style (`if (!self) { return nil; }`).
- UI is built from XIBs in `plugins/cocoaui/XIB` or next to their controllers; controllers are `*ViewController` /
  `*WindowController`.
- Cocoa-specific C helpers that need to be shared use `.c` files (e.g. `keyboard_shortcuts.c`), so they stay unit-testable.

GTK UI: user-visible strings are wrapped in `_("...")` for gettext.

## Tests and building

- macOS: use the Xcode `BuildProject` tool on `osx/deadbeef.xcodeproj`. The main scheme is `deadbeef`, and its test
  action runs the unit tests (`Tests` scheme). Other schemes: `Integration Tests`, `ddbcore`, `googletest`,
  `DeaDBeeF GTK2/GTK3`. CI equivalent:
  `xcodebuild test -project osx/deadbeef.xcodeproj -scheme deadbeef -configuration Release`.
- Builds are fast (incremental builds often take only a few seconds), because the project is almost entirely C and
  Objective-C, with no Swift and very little C++. A build that finishes in 1-2 seconds is normal, not a sign that it
  was skipped or is broken.
- Linux unit tests: `make -f Tests.mk` (GoogleTest, output in `testbuild/`).
- Unit tests are mostly GoogleTest (`TEST(SuiteName, case_name_expectation)`, e.g. `read_wrap_success`) in
  `Tests/*Tests.cpp`. They use the fake plugins `Tests/fakein.c`/`fakeout.c` and the bootstrap in `testbootstrap.c`.
  Add new test files to both `Tests.mk` and the Xcode `Tests` target.
- Prefer adding a regression test in `Tests/` for core and parser fixes (junklib, cueutil, tf, playlist, m3u, mp3parser, ...).

## Git conventions

- Commit subject: `<area>: <lowercase summary>`, where the area is a plugin or core module name (`junklib:`, `cocoaui:`,
  `gtkui:`, `mp4:`, `osx:`, `build:`, `streamer:`). Append `(fixes #NNNN)` when closing an issue. Short single-line subjects.
- The default branch is `master`. Big changes should be discussed first (see `CONTRIBUTING.md`).
- Don't commit generated autotools output, `testbuild/`, `.DS_Store`, or vim `*.un~` files.
